# main-check: stop the line when main is red
Read this before you merge a branch onto main, or when main is red.

- `budgit main-check` runs the project's full suite on a clean checkout of main's HEAD (a temporary detached worktree, removed afterwards) and records the result by commit sha. A result for the same sha is reused; `--rerun` runs it again. It prints the counts and the failing tests, and exits 0 when green, 3 when red.
- The suite is `test_command` from `.budgit/project.json`, which runs as shell and so needs the user's approval first (`budgit prepare --approve` in a terminal, or the standing yes); without one, `python3 -m unittest discover -s tests` when the project has a `tests/` folder. `test_timeout` (seconds, default 3600) bounds a run. `main_branch` names main when it is not `main` or `master`.
- The result file, the lock and the flag the hooks read live in the git directory (`budgit-main-check.json`, `budgit-main-red`): per clone, shared by its worktrees, and never tracked, so a reset or a commit cannot lose them. A red result sets `red_since`. It stays set until a later check on main goes green, and that closes an episode with its hours. `budgit main-check --status --json` shows `red_since`, the hours so far and the closed episodes, for the retro.
- `budgit main-gate on` installs two git hooks (`pre-merge-commit` and `reference-transaction`) that refuse a merge onto a red main. The one exception is the fix: a branch named `*-green`, or one marked with `budgit main-check --fix-for <branch>`. A refused merge commit leaves git's merge open and a following `git commit` is refused too; `git merge --abort` undoes it. The hooks cost one file test on an ordinary git command. `budgit main-gate off` removes the hooks. Existing hooks that are not Budgit's, and `core.hooksPath`, are never touched.
- After the fix merges, main stays red until `budgit main-check` goes green on the new commit. The merge gate is that check, run before every merge.
- Not gated: `git push` onto main, `git merge --squash` followed by a commit, `git cherry-pick`, `git rebase`, `git update-ref`, `git pull` (a sync), and `git push . x:main`. They are not merges of a branch, or they bypass hooks; the PreToolUse deny for `git merge` and `git push` is the planned second layer.

## Two full suites at a time on the machine, at low priority, never twice on the same tree
Several projects starting their full suite together overload the machine and make timing-sensitive tests fail for the wrong reason. `budgit main-check` and `budgit suite` therefore do these things before they run:
- **Slots.** They take one of two machine-wide slots (an flock on `suite.lock` and `suite.lock.1` under the Budgit home, released automatically if the holder dies) and wait for one to free up, printing `waiting for <n>s behind another suite (<what>, pid <pid>)` once a minute. `BUDGIT_SUITE_SLOTS` or `admit.suite_slots` in the home config changes the number; 1 is the old one-at-a-time queue.
- **Fair order (R-402).** Who gets a free slot is not whoever polls first. Every waiting suite is a ticket in `suite-queue.json` under the Budgit home: a release suite (`--release`) goes before every ordinary one; then the projects take turns (the project served least recently goes first, a project's lanes all count as one project), and inside one project the oldest ticket goes first. So a project with five lanes cannot keep another project's single suite waiting. Only one suite may wait per checkout: a second `budgit suite` from the same checkout exits 75 saying so. A ticket whose process died is dropped.
- **Load at start.** They print the machine load average at start and `main-check` keeps it, with the seconds queued, in its result (`load_start`, `waited`), so a timing failure can be judged against how busy the machine was.
- **Admission.** They ask `budgit admit suite` (see admit.md): while the 1-minute load average is above the core count they do not start: they print the load and the limit and exit 4. With `--wait` they wait and recheck every 30 s instead.
- **Low priority.** The suite command runs under `nice -n 10`, so hooks and the UI keep the CPU. `BUDGIT_SUITE_PRIORITY=background` uses `taskpolicy -b` instead and `=off` leaves the priority alone. `taskpolicy -b` is not the default because on Apple silicon it confines the suite to the efficiency cores (measured 4.5x slower than `nice` for the same work on an M3).
- **Same tree, no rerun.** A green run is recorded by the git tree (`HEAD^{tree}`), the folder and the test command, in `suite-green.json` under the Budgit home. `budgit suite` on a clean checkout of a tree that already ran green prints `this exact tree already ran green at ...` and runs nothing; it checks again once it has its slot, since the suite ahead of it may have been this very tree. `budgit main-check` does the same for a commit that has no result of its own but whose tree is known green (an empty commit, a merge that adds nothing to the branch tested before it), and its green runs feed the same store. Only green is recorded, only for a clean checkout (untracked files under `.studio/` and `.budgit/` do not count) that is still the same tree after the run. `--rerun` on either command runs anyway; `BUDGIT_SUITE_CACHE=off` turns the store off.

None of this runs inside a hook. A cached `main-check` result never waits and is never refused. A test that starts a nested run inside the suite passes through (the holder marks its children), so a suite cannot wait for itself. `budgit suite [--project]` runs the project's full suite (`test_command`, else unittest discovery) in the current checkout under the same rules. `BUDGIT_SUITE_LOCK` points the lock somewhere else and `BUDGIT_SUITE_LOAD_LIMIT` sets both load thresholds of admit (the tests use both, with `BUDGIT_SUITE_SLOTS=1` where a test holds the lock to queue behind it).

## Known bypass
`git merge --no-verify --no-ff` skips the `pre-merge-commit` hook by design, so a merge commit made with `--no-verify` completes on a red main (a fast-forward with `--no-verify` is still refused, because that check is a `reference-transaction` hook). Treat `--no-verify` on a merge as breaking the line on purpose.
